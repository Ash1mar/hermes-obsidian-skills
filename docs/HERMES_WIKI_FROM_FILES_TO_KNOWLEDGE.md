# 我们如何从文件生成 Wiki：解析、内容单元、知识构建与 WeKnora 对比

核对日期：2026-09-11。本仓库基线：`a74b631437541129b61dccb44f1101eab59dc567`；WeKnora 为当日核对的官方 main，不是固定发布版。本文只说明流程和设计建议，不代表已实施新的 chunk 层。

本文以我们自己的实际流程为主线，穿插解释三个容易混淆的问题：解析如何完成，chunk 究竟在哪一层，以及“Wiki 阅读材料”到底是什么。最后列出逐项对比表。

全文直接解释机制，不要求读者查看源码。所有示例编号、材料和建议字段均为说明性内容，不是已经生成的业务数据。

## 1. 先给出结论：我们不是没有知识构建，而是内容组织方式不同

我们目前有两条从文档出发的路径：

```text
原件 → 转换为 Bundle / 规范化 Markdown
         ├─ outline + ledger → 选范围阅读 → 候选判断 → 知识页 → 复核与来源登记
         └─ 获准进入索引的文本 → qmd-like-rag 切块 → Chroma / BM25 → 查询导航
```

这不是严格的先后调度图：原始文本与派生知识页都可能按配置和治理规则进入检索；知识构建不以 Chroma 先建好为必要条件。

关键区别是：

- **我们写知识主要使用 Bundle 正文的受控范围，不使用 Chroma 中的子块作为统一内容权威。**
- **WeKnora 将持久化 chunk 作为多个功能共同读取的内容记录；检索和 Wiki 可以复用同一来源 chunk。**
- 我们的 ledger 已经实现章节级逻辑划分及状态管理，但还不是一个独立的、统一服务于抽取与检索的内容单元库。

所以，下一步值得讨论的是“抽出 Provider 无关的内容单元层”，而不是“把 Markdown 拆成很多小文件”或“让所有治理都依赖 Chroma”。

## 2. 用一个例子说明我们到底在处理什么

假设收到三份材料：

| 材料 | 内容 |
|---|---|
| A：甲项目设备说明 PDF | 设备 P-101、组成、监测要求、表格和公式 |
| B：甲项目维护规程 Word | P-101 的维护条件、方法和适用范围 |
| C：另一个项目的说明 PDF | 也出现 P-101，但不是同一台设备 |

目标不是机械地生成三个摘要。我们希望从 A/B 整理同一对象的知识，避免与 C 混淆；对表格、单位和公式保留出处及 QA；后续查资料时能回到原文。

目前完成这件事的主体，是执行 controlled-ingest 的模型和工具组合，不是一个上传后自动运行所有阶段的后台 Wiki 服务。

## 3. 第一步：bootstrap 建的是工作环境，不是替我们读材料

新库由 bootstrap 创建目录、规则和模板，并根据选择建立治理骨架。旧库继续按兼容路径使用，不因没有新的治理配置就被自动迁移或重建。

建库时需要回答的是：

- 原件和知识页分别放哪里？
- 使用哪些通用摄取及写作规则？
- 是否启用来源机构和文档版本治理？
- 概念目录及页面模板如何使用？

bootstrap 不会因此知道 A 的技术结论，也不应凭目录名编出全部系统和对象。业务重点可以以后补充，不是启动通用知识构建的必要条件。

随后由 ingest 接手具体材料。bootstrap 和 ingest 的区别，可简单理解为“建好工作台”与“在工作台上加工材料”。

## 4. 第二步：保留原件，建立材料身份

原件保存在 `10_Raw/` 等约定位置，不被生成内容覆盖。启用治理时，通过 Governance Manager 登记逻辑文档、业务版本、资源及来源机构，并以实际文件计算指纹。

要区分四件事：

| 对象 | 举例 | 为什么不同 |
|---|---|---|
| 逻辑文档 | 甲项目设备说明 | 不同业务版次仍可能属于它 |
| 业务版本 | A版、B版 | 需要业务依据，不由文件修改时间决定 |
| 原件资源 | 某个具体 PDF 字节文件 | 哈希证明是否同一份字节内容 |
| 解析产物 | 某次 MinerU 生成的规范正文 | 同一原件重解析，文本和行号也可能改变 |

材料身份清单解决以上身份，不是写作偏好清单。“重点关注维护”不会替我们决定这份文件属于哪个业务版本。

旧 Vault 没有启用 registry 时，仍可保留原件、转换、分章和构建；但不能声称它已经获得同等的多机构、业务版本治理能力。

## 5. 第三步：我们具体怎样解析文件

### 5.1 工程 PDF：MinerU 解析，我们的转换器组织结果

当前主路径不是直接把 MinerU 输出的 Markdown 原样放进知识库。

具体顺序是：

1. 转换脚本接收原 PDF、输出位置及解析配置。
2. 在 WSL 通过 MinerU CLI 执行，或通过配置的 MinerU HTTP 服务执行；也可复用已有 MinerU 输出。
3. MinerU 负责从 PDF 获取版面、文字、公式、表格和图片等解析结果，具体效果取决于选择的 backend、method 和模型。
4. 我们的 Bundle 渲染主要消费原 PDF、选定的扁平 `content_list.json` 及其引用资产，而不是默认把全部中间 JSON 都变成正文。
5. 将结果整理为一个规范化 `document.md`，加入页锚点，组织标题层级，链接图片，将复杂表格单独放入 `tables/`。
6. 生成 `outline.json`、资产清单、来源及转换信息，保留选定 `_evidence/` 供 QA 回查。
7. 验证 Bundle 的文件、范围、引用及结构一致性，形成 pass/warn/fail 等结果。

例如，A 的一个参数表不是必须挤成 `document.md` 的一个巨大 HTML 行。正文可以保留表格标题与链接，模型需要该表时再打开表格文件和对应图像证据。

这使我们的规范化产物更像一个可审核的资料包，而不只是喂给检索器的一串文本。

注意：扁平 content list 缺失时的 Markdown 回退是不完整路径；默认保留的部分 `_evidence` 也不保证足够独立重建整个 Bundle。解析质量通过结构检查，不等于公式语义已经正确。

### 5.2 Word 等其他格式

仓库有 MarkItDown 转 Markdown 的工具：优先使用 Python API，并提供 CLI 路径。它是格式转换工具，不是通用 Bundle v2 生成器。

因此，B 转成 Markdown 并不自动拥有与工程 PDF 相同的页锚点、表格资产、章节 ledger 及治理投影。哪些格式已具备完整治理链路，要按具体输出检查，不能把“能转 Markdown”说成“所有格式已统一受控摄取”。

对于受治理知识构建，如果格式缺少必要的身份及 ledger 链接，需要报告限制；不能为了继续写页而绕过可见性控制。

### 5.3 独立图片

图片有独立的 Bundle v2 路径，可以接入 OCR 文本文件或 OCR 命令，并保留原图。OCR 文本标为派生且待核验；无 OCR 时保留视觉证据，不能假装已经有可靠正文。

这与 PDF 中的一张插图不同：独立图片可能就是全部来源，所以不能仅把它作为附件而忽略其来源身份。

## 6. 在解析这一步，WeKnora 具体怎么做

### 6.1 它用“解析引擎路由”，不是所有文件都走 MinerU

应用根据格式、知识库设置及有效覆盖配置选择 Reader。不同 Reader 返回统一形态的阅读结果，核心是 Markdown 内容、图片引用及相关元数据/错误。后续存储图片、切块和索引不需要逐个适配每一种解析器的原始输出。

当前可见的路线包括：

| 路线 | 怎么处理 |
|---|---|
| Go 的 simple reader | Markdown/TXT 直接读文本；CSV 转表格 Markdown；JSON 经转换；图片先包装为图片引用 |
| Python DocReader | 按格式选专门解析器，例如 PDF、DOCX、Excel；部分格式使用 MarkItDown |
| anydoc | 构建中可用且支持该格式时，提供进程内办公文档转换 |
| 自部署 MinerU | 调用配置的 HTTP 端点，接收 Markdown 与图片等结果 |
| 其他配置引擎 | 如 MinerU Cloud、PaddleOCR-VL、自有云 Reader，取决于服务及凭据是否可用 |

支持某个引擎，不等于一次上传会把所有引擎都跑一遍，也不表示缺少配置时能神奇回退成功。

### 6.2 内置 PDF 不是“直接 OCR 整个文件”

所查 Python PDF 路径使用 pypdfium2，逐页判断页面更像原生文本还是扫描图像。判断会参考图像覆盖面积等信息，而不只数有多少字符：扫描页也可能带着质量很差的隐藏 OCR 文字层。

- 原生文本页：抽取文本，并处理可用的内嵌图片。
- 扫描页：渲染为图片，标识扫描来源，由应用侧后续 OCR/VLM 处理。
- 混合 PDF：可以不同页走不同处理方式，而非给整份文件一个粗暴结论。

所以 DocReader 本身“产生页面图片”不等于已经完成 OCR，真正可用性还取决于后续多模态处理配置与结果。

### 6.3 Word 与 MinerU 路线的具体区别

Python 内置 DOCX 路径会解析文档结构、段落、表格和图片；其解析实现使用 python-docx 等工具。另有 MarkItDown 等可选路径，不应把所有 Word 都描述为“先变 PDF 再 OCR”。

自部署 MinerU Reader 则把文件发送到服务，携带解析方法、公式/表格等设置，取回 Markdown 和图片；再做针对性的 Markdown/表格兼容处理、解码图片并统一图片引用。它并不按我们的 Bundle 规范重新建立 `outline + ledger + QA reports`。

### 6.4 和我们的解析区别总结

| 比较项 | WeKnora | 我们 |
|---|---|---|
| 解析入口 | 应用统一 Reader，按配置路由 | Skill 选择并调用转换脚本 |
| 工程 PDF 主实践 | 可选内置、MinerU 等路径 | 重点建设 MinerU → 工程 Bundle |
| 中间结果组织 | 统一阅读结果，继而切块入库 | 单一规范正文 + outline + 外部资产 + QA 证据 |
| 图像处理 | 可继续生成 OCR/描述型内容记录 | 默认避免解释所有图像，针对所需证据核验 |
| 格式统一程度 | 多引擎统一应用接口 | 工程 PDF/图片 Bundle 较完整，其他转换不能视为同等闭环 |
| 质量边界 | 解析成功也不证明业务事实正确 | Bundle 验证同样不证明公式、参数语义正确 |

我们不是需要重做一个 OCR，而是需要判断：是否在现有 Bundle 之后增加统一内容接口，让后续不再各自解释解析产物。

## 7. 第四步：outline 和 ledger 怎样把内容划成可处理范围

### 7.1 outline 管结构，ledger 管处理责任

`outline.json` 描述章节、层级、行范围、页及资产。Bundle Manager 将它转换为可恢复的处理单元，并在 ledger 中记录状态、哈希、输出和 QA。

例如：

```text
章节 3：100–180 行
  子章节 3.1：120–140 行
  子章节 3.2：150–170 行
```

不能让“章节 3”再次完整摄取 100–180 行，否则会重复读写子章节内容。ledger 的逻辑是：父章节只拥有扣除子章节后的自有范围。

示意结果：

```text
章节 3 的 content_ranges：100–119、141–149、171–180
章节 3.1 的 content_ranges：120–140
章节 3.2 的 content_ranges：150–170
```

这是真正的范围划分，不是装饰性目录；但一个处理单元可能由几段不连续文本组成，也可能很长。

### 7.2 为什么它还不等于 WeKnora 的 chunk

当前 ledger 主要回答“哪些章节已读、由哪个运行处理、产出了什么”。它不是按固定长度生成小块正文的算法，也不将每个范围都注册成通用 chunk 记录。

我们已经有：章节 ID、范围、范围内容哈希、资产、QA、状态和输出关系。

我们还没有：全流程统一的 chunk ID、独立的精确块内容读取接口、统一块级生命周期，以及从 Wiki 到 Provider 的同一套内容引用。

因此更准确的称呼是 **受控的逻辑阅读单元**。它具备部分 chunk 能力，但职责以流程和章节治理为中心。

### 7.3 不必复制成很多小 Markdown 才算“真切块”

切块至少可以有两种有效实现：

- 存正文副本：每条记录带内容、来源、范围和指纹。
- 存可验证切片：记录身份、不可变来源版本、范围和指纹，通过接口准确取回内容。

两者都可以是真正的内容单元。决定是否成熟的不是“有没有一千个小文件”，而是身份、范围、读取、变更和引用是否一致。

我们现行 Bundle 规则明确避免每章节另存正文副本，以免与 `document.md` 漂移。未来引入 chunk 并不必然推翻这条规则。

## 8. WeKnora 到底怎样切 chunk

### 8.1 切块发生在解析之后，由 Go 切块器执行

主路径是：解析取得 Markdown → 处理图片引用 → 规范化换行与文本 → 读取有效切块配置 → 切块 → 保存 chunk 并建立索引及后处理。

不是由 Chroma 自动替它切，也不是要求 LLM 自由决定所有边界。它有确定性的切块程序和策略选择。

### 8.2 不是只有“每 512 字截一刀”

策略有递归、标题、启发式与自动选择等路线：

| 策略 | 实际做法 |
|---|---|
| recursive / legacy | 优先用分隔符切成小单位，超长部分继续递归，再按预算合并 |
| heading | 识别 Markdown 标题结构，按标题边界分段；长章节内部继续切，保留标题上下文 |
| heuristic | 对标题不规范的文本，识别编号章节、分页、分隔线等边界，累积成块；超长部分回到递归切分 |
| auto | 检查文档结构特征，选择策略链；结果不满足相应检查时回退 |

一个重要兼容细节：所查实际分支里，空策略保留 legacy；不能看见某处注释写“自动”就宣称所有旧库都会启用自动策略。最终取决于有效配置。

### 8.3 递归路径如何工作

默认配置常量为 512 个字符、80 个字符重叠，分隔符包含空段、换行和中文句号。这里主要是 Unicode 字符计数，不是我们 Provider 的 800 token。

处理可理解为：先识别公式、代码、链接和表格行等受保护结构；普通长段按优先分隔符细分；把相邻单位合并到预算附近；块尾在合适边界保留有限重叠。极大结构仍有安全截断，不能宣称完整大表绝不拆分。

重叠不是机械地必留 80 字：会受语义边界和下一块预算影响，没有合适边界时可能不保留。

### 8.4 标题、上下文和坐标不能混在一起

标题策略中，短章节可以直接成为一块；长章节再细切。标题层级形成 `ContextHeader`，与正文内容分开保存，以便索引时加上“它属于哪一章”的语境。

chunk 的 `Start/End` 是规范文本中的字符偏移，不是 PDF 页码，也不是 bbox。设计上尽量让内容与来源切片对应；但旧路径存在补表头等合成上下文处理，不能仅凭字段就承诺所有策略输出都字节级等同于一个纯原文切片。

这对我们的启发是：必须明确“原文核心范围”与“为理解追加的上下文”，不要把追加文字混入原文定位。

### 8.5 父子块具体怎么做

启用父子模式时，先按父配置切，再在父块内部按子配置切，子块偏移换算回整份规范文本坐标，并关联父记录。所查回退默认父大小为 4096 字符、子大小为 384 字符；实际知识库可以覆盖，不是所有用户都用这些值。

父块主要提供上下文，不参与该父文本类型的向量索引；子文本块参与检索。只有需要独立父上下文时才保留对应父记录，不能假定每个子块一定产生一个单独父副本。

另有近似 token 预算能力，其语言比例估算并非精确 tokenizer。不要直接将这些数值与我们 cl100k_base 的 token 数对比。

### 8.6 切完之后存什么

持久化记录不仅有正文和向量键，还包括 chunk UUID、所属材料/知识库、类型、序号、起止位置、前后块、父块等。模型中另有源内容、编辑修订、启用状态和索引状态。

所以 chunk 是应用层内容对象，不只是向量库临时切片。但是 UUID 在创建时分配，不能由此推定重解析后相同文本一定保持同一个 ID。

它的 chunk 类型还覆盖 OCR、图片描述等派生内容；**被叫作 chunk，不代表内容都是原始证据**。来源文本、模型派生描述和 Wiki 产物必须继续区分。

## 9. 这些 chunk 和狭义 RAG 的 chunk 是不是一回事

### 9.1 在 WeKnora 中，来源正文块确实被复用

不是先创建一套只给 Wiki 的段落库、再完全独立创建一套 RAG 原文块。Wiki 流程会从应用的 chunk 仓库取该文档内容，关联候选与 chunk ID，写页时按 ID 取回相关原文。检索则对符合条件的块建立索引。

因此是 **共享内容记录，多种消费方式**。但不是所有 chunk 类型都参与同一种索引或 Wiki 阅读：父文本、OCR 子块、摘要、Wiki 页等有各自用途。

### 9.2 同一份内容，可以有不同大小的消费窗口

RAG 关心召回时哪个窗口好匹配；知识构建关心某个对象需要哪些完整证据。共享来源身份，并不要求所有任务每次读完全相同大小的一块。

示例：

```text
原文内容块 c1：设备用途
原文内容块 c2：适用条件
原文内容块 c3：例外条款

检索窗口可能强调 c2；
写完整知识页时必须连 c1、c2、c3 一起考虑。
```

不能因为检索命中 c2，就假定它已经是足够独立的最小业务事实。chunk 是内容组织单位，不等于原子 Claim，也不等于本体实体。

## 10. 我们的 qmd-like-rag 实际怎样切块

### 10.1 切块的是 Provider 代码，不是 Chroma

qmd-like-rag 扫描符合配置和治理条件的 Markdown，调用自己的 chunker。Chroma 接收已经切好的文本和元数据，保存/索引它们；BM25 也使用这一 Provider 产生的块。

具体步骤如下：

1. 读 Markdown，统一换行。
2. 用 `#` 到 `######` 的标题行识别边界。
3. 每遇一个新标题，结束前一个父段，保存父段正文、标题路径及开始/结束行。
4. 对父段调用子块切分：不超限直接保留；超限按 tokenizer 的窗口切分并重叠。
5. 为子块生成 ID，带上父段、来源指纹和位置等信息。
6. 将这些记录送入 Chroma 和 BM25。

默认 `chunk_size=800`、`chunk_overlap=0.15`；有 tiktoken 时使用 `cl100k_base`，滑动步长为 `int(size × (1-overlap))`。依赖不可用时退到正则计数与单位切片，并不是完全等价的 token 划分。

父段是“相邻标题之间的段”，不是 Bundle outline 的父章节完整树范围。当前这段标题检测也不是完整 Markdown AST 解析器，因此不能等同于有代码围栏保护的结构解析。

### 10.2 ID 和行号有什么限制

ID 对来源路径、父段起止行、标题路径和子块正文等拼接结果取 SHA-256。相同输入可以重现；但移动文件、插入前面的行或改变标题，可能使 ID 改变。内容指纹和业务稳定身份不是一回事。

**目前每个子块保存的 start_line/end_line 都是父段的范围，不是子块精确行范围。**

例如父段是 100–220 行，切成三个子块后，三者都可能记录 100–220。它支持回读父段，但不能证明某个数值就在子块对应的特定几行。

Chroma 中还保存了 `parent_text`，有助于回填上下文；这也不让它自动成为治理权威。

### 10.3 为什么不能直接拿这套 ID 当未来内容治理主键

- 它属于可重建 Provider 状态，默认在运行主机上，不属于 Vault 的权威资料。
- 切块配置变化会改变边界。
- 子块有重叠，直接按块统计或抽取容易重复。
- 当前行号粒度是父段，缺少子块精确 locator。
- 没有统一继承 Bundle 章节、页、资产、QA 和业务版本的完整契约。
- 没有作为全流程内容服务提供稳定的读取及变更接口。

它适合目前的粗召回职责；若要用于统一知识治理，需要显式升级，不能仅因为 Chroma 已经存了文本就把它变成事实来源。

## 11. 三种“块”放在一起看

| 特性 | 我们的 ledger 单元 | 我们的 Provider chunk | WeKnora 来源 chunk |
|---|---|---|---|
| 主要边界 | 章节的非重叠自有范围 | Markdown 父段 + token 子窗口 | 配置策略切分的字符/结构范围 |
| 是否可能很长 | 是 | 父段可能长；子窗口受预算约束 | 父子配置、保护结构和安全限制影响大小 |
| 是否重叠 | 自有阅读责任尽量不重叠 | 子窗口可重叠 | 可配置重叠，不总是精确固定长度 |
| 是否保存块正文 | 主要通过正文范围读取 | 保存子文本及父文本 | 应用内容记录保存正文 |
| 工作状态 | 领取、完成、QA、stale 等 | 索引同步状态 | 内容/启用/索引等应用状态 |
| 精确位置 | 声明的正文行范围 | 子块沿用父段行范围 | 规范文本字符偏移等 |
| 当前是否写 Wiki 的共享输入 | 是，以范围为主 | 不是统一权威输入 | 是，正常引用路径复用 |
| 能否丢弃重建 | ledger 有审计状态，不能随意丢 | 默认可重建 | 内容编辑及引用使其不等同于纯向量缓存 |

这个比较说明，我们缺的不是“能不能把文本分短”，而是**让同一个可引用 canonical chunk 同时服务知识构建与检索，并把索引渲染和来源核心明确分开**。

## 12. 第五步：准备“Wiki 阅读材料”——它不是另一种 Wiki

### 12.1 先纠正术语

前文的“Wiki 阅读材料”是解释性称呼，不是 WeKnora 必须生成的一个同名文件、页面类型或额外知识库。更准确应叫 **送给知识构建模型的输入上下文**。

它与读者最终看到的 Wiki 正文不同：

| 层次 | 例子 |
|---|---|
| 来源 | 原 PDF、规范正文、表格/图像 |
| 输入上下文 | 本轮读取的正文、相关片段、旧页、身份和规则 |
| 输出 | 模型整理出的知识页面 |

### 12.2 WeKnora 怎么准备

候选发现和文档摘要需要了解文档整体，所以它会从 chunks 重建文档文本，必要时带入已有 OCR/图像描述信息。

chunk 关联阶段则发送候选列表和分批片段，让模型判断归属。写某一页时，再组装该页旧正文、关联原文、文档摘要语境、来源变化和允许链接。

因此不是有一份万能“阅读材料”喂给所有阶段，而是不同阶段有不同输入窗口。这些组装结果可以是运行时字符串，无需成为永久 Wiki 页面。

### 12.3 我们对应的步骤是什么

我们由执行者读取：规则与任务范围、manifest/outline/ledger、选定 `content_ranges`、必要表格或图片、已有相关知识页。

这些共同构成模型的工作上下文。`inspected_ranges` 是“本次声明检查了哪里”的审计记录，不是完整上下文副本；source-map 是导航和状态视图，也不是正文替代品。

当前没有统一的上下文组装服务，自动输出“某对象的完整编辑任务包”。组织上下文主要依赖 Skill 执行者，这是与 WeKnora 服务编排的重要差别。

## 13. 第六步：从读到的范围里提出候选

执行者不应读完一段就立刻建一页，而是先判断可组织的知识：实体、概念、要求、事实或分析。

在示例 A/B 中，可能识别出：

- 实体：甲项目 P-101。
- 概念：某种监测方法。
- 要求：在特定条件下执行某操作。
- 事实：来源描述的组成或参数。
- 分析：A/B 对同一事项的描述差异。

这些是通用角色，不是预先加载的专业本体。不会因为分类叫 requirement 就已经校验了义务主体、条件、例外的完整逻辑。

执行者为本次构建建立 v3 记录，写下实际阅读范围、候选名称、理由和证据。无候选也要说明检查了哪里、为何没有产出；不能空跑脚本就报告“已构建”。

## 14. 第七步：查已有页面，决定如何处理

对于 P-101，要先确认已有页是不是同一个对象。A/B 同属甲项目，可能支持同一页；C 是另一项目，即使同名也不能直接归并。

执行者记录身份判断，并选择：

| 动作 | 实际含义 |
|---|---|
| create | 有独立价值，需要新页 |
| update | 对已有页新增或修订内容 |
| reuse | 已有页足够，不重复创建 |
| relate | 对象不同，只建立相关关系 |
| defer | 身份、证据或权限不够，暂缓 |
| skip | 检查后明确不构建，并解释原因 |

我们有这些动作的记录与结构校验，但没有 WeKnora 那样的数据库候选预筛选、并发 slug 协调和自动分组服务。主要是 agent 查找、阅读和决定。

因此，规则上要求区分项目，不等于程序已经用完整业务键自动消歧。验收还要看实际页面有没有混同。

## 15. 第八步：把证据与候选绑定，再写页面

当前绑定形式主要是：来源路径、来源文本 SHA-256、行范围、QA，以及对应 Bundle/ledger/section 信息。

如果某项分析来自 A 的参数表和 B 的维护条款，应记录两份实际支持范围，不可只引用一个总摘要。

遇到 QA，不是只有“全跳过”或“当作正确”两种处理。v3 可以保留带具体 `qa_note` 的归属明确草稿，要求 needs-qa 不被改标 usable，受影响页保持 draft，并同步 QA 说明。解析失败、身份不一致或访问受限的内容不能因此获得许可。

写作落点仍采用现有 Notes、Cards、Concepts、Projects 等模板规则。概念需要遵守现有概念治理；主题索引不能伪装成具体项目。

我们不会自动为每份材料强制生成 WeKnora 式摘要页，也不会自动生成一棵新的对象分类树。文件夹和概念目录是现有工作体系，不是每批候选集中规划出的分类服务。

## 16. 第九步：多份材料如何汇成同一知识页

我们已经允许一个候选或一个输出依赖多份来源，不局限“一页一来源”。实现方式是执行者主动汇集证据、决定 update/reuse/relate，再写入目标页。

示例：

```text
A 的组成说明 + B 的维护条件
  → 对照“甲项目 P-101”旧页
  → 判断内容是否重复、冲突或补充
  → 形成有来源归属的新正文
```

我们借鉴了“先候选、后证据、再编辑”的思想；但还没有一个自动 Map/Reduce 引擎，把所有文档贡献持续按稳定对象 ID 汇总为写页任务。

这一区别不应被“支持多来源”四个字掩盖：**多来源表达能力已经有，自动化汇总调度尚未做到同等程度。**

## 17. 第十步：复核最终正文，生成来源投影

当前 v3 的收尾不是“文件保存成功”就结束：

1. 写好正文，检查来源归属、适用范围、冲突和 QA。
2. 运行 provenance 预览，取得排除工具来源块后的正文指纹。
3. 执行者对照证据复核，填写 `output_reviews`；项目页补充项目依据。
4. apply 同步来源块，并将输出登记到每一个支持它的 Bundle 章节。
5. 确认章节终态，设置本次构建完成，运行 complete 校验和 lint。

同一页由多个候选支持时，来源同步器按输出汇总证据并集。它不是 LLM 写作器，也不是自动审批器。

此处的来源并集还是页面级，不是逐句 Claim—Evidence 的形式化证明。`finding` 非空及指纹匹配，也不证明复核者理解正确。

## 18. 第十一步：维护与检索

来源重解析后，Bundle Manager 协调范围及哈希，识别 stale，保留原输出供复查；执行者重读并判断如何更新。没有全库知识页自动撤回与重写服务。

页面和所有支持来源的关联完成后，按授权同步 Provider。索引只接收配置及治理允许的数据，draft 字段本身不是完整访问控制。

未来业务版次激活仍由治理流程完成。知识页完成、来源处理完成、业务版次 active、向量索引 ready，是不同状态。

这也是为什么不能让“Chroma 里有这个 chunk”成为唯一的知识完成判断。

## 19. 如果希望 chunk 成为通用内容单元，建议怎样演进

本节最初是设计建议。2026-09-15 校正后，P2 已把 SourceUnit 实现为知识构建与 RAG 共用的 canonical chunk；早期“Provider 可普遍另切检索窗口”的建议已撤销，阶段状态以 ADR-0003/0004 和演进计划为准。

### 19.1 建议目标

将目标表述为：

> 建立 Provider 无关、可定位、可校验的 canonical chunk，供抽取、引用、QA 和检索共同消费；Provider 默认一 Unit 一索引文档，只附加可重建的标题/模型渲染。

不要表述为“所有数据最小单位只能是 chunk”。表格单元格、图像区域、公式和单个 Claim 可能需要更细 locator；章节又可能是更大的完整阅读上下文。

### 19.2 三层分开

| 层 | 建议职责 |
|---|---|
| canonical SourceUnit/chunk | 身份、原文核心范围、版本、指纹、配置化 overlap、资产和 QA；由知识构建与 RAG 共享 |
| 工作窗口 | 为抽取某对象组合若干内容单元及上下文 |
| 索引渲染 | 默认一个 Unit 对应一个索引文档；添加标题上下文并测量 tokenizer，保存 UnitRef 和投影指纹 |

SourceUnit 的 chunk size/overlap 变化会形成新 UnitSet；工作窗口和索引渲染可随任务、模型变化。重叠 Unit 按范围并集计算原文覆盖率。只有模型硬上限或 oversized 特例才允许显式 subspan，不建立第二套普通 chunk。

### 19.3 可以借鉴 WeKnora，但保留我们的证据边界

值得借鉴：解析接口与切块解耦；结构优先的确定性切块；内容与附加标题分开；父子/相邻关系；应用层 chunk 记录；Wiki 与检索复用来源身份。

不要直接照搬：把可编辑 chunk 或 Provider 记录当成唯一原文；未经规则定义就声称 UUID 跨重解析稳定；为了不断运行而用候选描述替代缺失的证据。

我们应继续保留原件和规范正文，把 chunk 当可验证的组织层，而不是又一个可以随手修改却无来源版本的正文副本。

### 19.4 一份最小契约应该回答什么

下列是字段职责草案，不是可执行 JSON schema：

| 职责 | 必须明确的问题 |
|---|---|
| 身份 | 单元 ID 如何生成，重解析、重切块、移动文件时哪些 ID 改变？ |
| 来源 | 属于哪个资源、业务版本及规范化产物版本？旧 Vault 没有业务版本时怎么办？ |
| 定位 | 核心文本的行/字符范围是什么？表格、图片资产怎样定位？ |
| 内容一致性 | 取回的正文是否与记录指纹一致？上下文是否明确标为附加？ |
| 结构 | 所属 section、父/邻接单元以及资产关系是什么？ |
| QA | 哪些单元受限制，限制怎样传给知识页和检索？ |
| 切分来源 | 使用哪个算法及配置指纹生成？ |
| 更新 | 新旧单元如何关联，已引用旧单元的知识页如何变 stale？ |
| Provider 映射 | 普通索引文档是否恰好钉住一个 UnitRef？例外 subspan 是否有明确原因？ |

任务领取、执行进度仍可以留在 ledger，不必全部搬入内容单元本身。

### 19.5 小规模实践顺序

1. 选一份已经验证的 Bundle，不重建旧 Vault。
2. 只读生成候选单元清单，采用“章节自有范围内再细分”的方式，不跨业务来源混合。
3. 提供按单元读取与校验能力，先验证定位、内容覆盖和资产关系。
4. 让新知识构建直接记录 UnitRef，不继续维护旧行范围双轨。
5. 让 Provider 直接索引同一批可用 Unit，删除 Provider 独立文档切片；只独立调整 embedding/标题渲染。
6. 验证重解析/切分参数变更后，旧引用能被识别而非悄悄重定向。

这可以先基于文件清单实现，不以立即引入数据库为前提。数据库是存储后端选择；清晰的单元契约才是这一轮工作的核心。

## 20. 最后逐项比较：类似的实践、差异和未实现部分

“已有”仅指当前代码或明确 Skill 工作方式存在，不代表实际 Vault 已全部执行；“agent 规则”也不等于自动服务保证。

| 环节 | WeKnora 实践 | 我们当前实践 | 对齐程度/缺口 |
|---|---|---|---|
| 原文件保存 | 存储服务与材料记录 | 原件保留，启用时 registry 登记 | 目标相近，后端及产品化程度不同 |
| 解析路由 | 统一 Reader，多引擎 | Skill 调用不同转换脚本 | 有多工具，缺统一内容返回契约 |
| 工程 PDF | 内置逐页路由或 MinerU 等 | MinerU + 工程 Bundle | 路线可重叠，产物组织明显不同 |
| Office | 专门解析器/anydoc/MarkItDown 等 | MarkItDown 转 Markdown | 能转换，不代表已达到 PDF 同等治理闭环 |
| 图像证据 | 图片存储、OCR/描述子记录 | 图像资产、图片 Bundle、针对性 QA | 都保留图像；派生内容策略不同 |
| 规范正文 | Reader 结果继而入 chunk 仓库 | 单一 `document.md` 为规范文本 | 我们更依赖文件式来源 |
| 结构划分 | 标题/启发式/递归切块 | P2 outline owned ranges + 结构/启发式/递归 canonical chunk | 来源层已对齐，策略细节仍不同 |
| 检索子块 | 配置切块，应用库持久化 | P2 UnitSet 已持久化；旧 Provider 仍保留标题父段 + token 窗口 | P5 必须删除旧独立切片并直接索引 Unit |
| 精确子块定位 | 规范文本字符坐标等 | P2 Unit 使用规范文本 codepoint 精确范围 | 来源定位已补；Provider 透传留到 P5 |
| 共享内容单元 | 来源 chunks 被 Wiki 和检索消费 | P2 canonical Unit 已成立，P3/P5 将分别接入知识构建和检索 | 内容对象已对齐，消费者接线未完成 |
| 模型输入组装 | 服务按阶段自动组装 | agent 阅读规则、正文及旧页 | 有操作方式，缺统一组装器 |
| 通用候选发现 | 实体/概念等提示流程 | entity/concept/requirement/fact/analysis | 思想相近，类别与执行方式不同 |
| 同一性判断 | 预筛选、模型判断、名称/slug 协调 | agent 查旧页及理由记录 | 有语义规则，缺同等自动协调 |
| 候选证据绑定 | 候选到 chunk；存在降级路径 | 候选到指纹/行范围/章节/QA | 已实现不同形式，不是同一契约 |
| 文档摘要 | 独立摘要页及生成阶段 | 不强制每份材料生成摘要页 | 尚无同等固定阶段，未必必须照搬 |
| 多来源汇总 | 按页面身份批量汇聚贡献 | agent 主动汇集，记录多来源 | 内容能力有，自动 Map/Reduce 调度无 |
| 分类目录 | 整批规划并复用既有目录 | 现有目录/模板/概念治理 | 没有同等自动 taxonomy 规划 |
| 正文写作 | 编辑模型 + 旧页及来源变化 | Skill 模型按候选证据写作 | 方法相近，程序编排程度不同 |
| 复核与来源投影 | 应用页面及引用维护 | v3 复核指纹、同步器、complete 校验 | 有自己的闭环，非逐句事实证明 |
| 页面关系与索引收尾 | 自动链接整理与 finalize | agent 维护，lint 检查 | 没有同等全库自动收尾服务 |
| 来源更新 | 增补/撤回任务 | ledger stale/orphaned，人工或 agent 重读 | 检测已有，自动重写/撤回缺失 |
| 后台恢复 | 持久任务、批次、重试及终结失败 | ledger 修订检查及恢复规则 | 可续作，但不是持续后台服务 |
| 业务版本治理 | Wiki 修订不能替代业务批准 | 独立文档及机构 registry | 我们明确另建治理线，不应混为能力对等 |
| 多领域本体 | 通用 Wiki 不等于本体硬约束 | 通用角色亦不等于本体硬约束 | 两边本文所述流程都不能作此保证 |

## 21. 对下一步的判断

你提出的方向有实质意义：让 chunk 不只是“给向量检索切出来的一段文本”，而成为知识构建能稳定引用的来源单元。

新体系保留 Bundle 的解析产物职责；ledger 退回工作与审计控制面。P2 已补齐 Provider 无关的 Unit 身份、精确读取、QA 继承和 canonical chunk overlap。P3 与 P5 应消费同一 UnitSet，其中 Provider 只做索引渲染，不能恢复自己的普通切片权威。

这项改造和“换数据库”“重写 OCR”“增加本体”是不同工作。建议先验证最小内容单元契约，避免同时扩大所有层的范围。
