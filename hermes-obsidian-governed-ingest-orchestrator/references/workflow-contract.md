# Workflow contract

The authoritative record is `_system/ledgers/ingest-workflows/<workflow_id>.json` in the Vault. `start` requires `workflow_id` (`ingest-...`), `actor`, `profile` (`compact-3` or `diagnostic-6`), `scope`, `expected_revision: 0`, and `input_digest`. An existing knowledge-build `batch_id` is optional. See the canonical `ingest_workflow` JSON schema in `lib/hermes_source_units/schemas/contracts.json` for scope details.

For mutations, calculate `input_digest` as `sha256:` plus the canonical request fingerprint excluding `input_digest`; the `digest` CLI command can do this. Use the record's current `revision` as `expected_revision`. Do not regenerate a workflow ID on retry. A duplicate start with identical digest returns the existing record; a different digest is a conflict.

`template_pins` contains one entry per worker kind: `kind`, versioned `template_id`, `template_hash`, and Vault-relative snapshot path. Pinning stores the exact UTF-8 template bytes in the workflow's Vault directory. Once pinned, the set cannot be replaced. Dispatch verifies every snapshot hash before creating active cards; missing/changed content fails closed. Changing Skill files affects only new workflows. Kanban task idempotency keys also include the pinned template hash.

The Vault owns source, batch, Pass, Reduce, release, checkpoint and final acceptance state. Kanban tasks are only rebuildable projections. A card reaching `done` does not prove that its domain operation succeeded; reconciliation checks Vault state. `source_outcomes` records each scoped source path, verified raw SHA-256, `ready` or `failed` status, validated current UnitSet identity for ready sources, and a typed error/reason for failed sources. Compact status exposes requested, ready, failed and pending coverage. A failed source card is terminal for that source and lets the remaining source cards proceed. `exact-plan` waits for all outcomes, then accepts only a batch covering the ready UnitSets. Zero ready sources block planning; final acceptance must be `partial` while failed sources remain.

`profile` controls only the read-only `display` object returned by compact status: phase number, total, name and pending checkpoint. It does not change transition order, worker graph, budgets, idempotency keys, approvals or authoritative stage. The mapping is documented in `compatibility-profiles.md`.

`scope.execution_mode` selects `manual` (default), `canary_only` (stop after eight Pass slices), or `auto_full`. `dispatch_policy` is Vault-authoritative and starts disabled. Scoped source preparation and exact planning may dispatch before Pass canary arming. `canary-preview` chooses at most eight ready slices without writing; `arm-canary` requires the exact IDs, digest and expected workflow revision. The first selection is immutable. In `auto_full`, sync arms exactly eight ready slices; fewer than eight yields `canary_unavailable` and no Pass dispatch. It promotes to `full` only after all eight have durable valid Pass results. `full` permits remaining Pass slices and the downstream graph. In manual mode disarming stops later Pass worker checks and rearming is limited to the original IDs.

Each auto checkpoint has a persisted validation report and decision file under the workflow ledger. The decision binds the workflow ID, checkpoint, approval digest, result and blocking codes. The workflow service verifies the file hash and rechecks current batch or release plan and lint evidence before recording `approved_by: hermes:auto`. A changed decision or changed underlying Vault input fails closed. Manual approvals remain available. A failed auto check blocks that card; it does not advance the gate.
